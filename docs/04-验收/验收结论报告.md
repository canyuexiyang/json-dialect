## 五、本轮修复的真实缺陷

验收过程中发现并修复了 7 个「写了但不生效」的问题，均非新功能缺失，而是实现与验收标准存在落差：

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | 注释剥离未计入修正记录 | AC-19 不成立 | `convert()` 保留 `lex().marks`，状态判定改为以 fixes 为空为准 |
| 2 | Map 值内部空格被吞（`hello world`→`helloworld`） | 数据损坏 | `ParseOptions.rawText` 传原文 + 自写 `stripComments()` |
| 3 | bool/null 字面量作键直接报错 | 与 FR-A16 取舍原则不一致 | 宽松模式转字符串键并记修正 |
| 4 | 放大页只继承输入文本，锁定/模式/覆盖全丢 | AC-33 不成立 | 新增 `InheritedState` 完整继承 |
| 5 | 改类型后 `state.output` 未更新 | 复制/下载拿到旧输出 | 同步更新 `state`（AC-39 同类隐患） |
| 6 | `dist/` 缺 `manifest.json` | **产物无法加载** | build 后增加 `tools/copy-manifest.mjs` |
| 7 | **UI 初始化被 storage 拖死**：`await loadPrefs()` 排在 `createEditor()` 之前 | **真机 P0：扩展完全不可用**（布局正常但输入区点不动、粘贴不进） | init() 拆为「同步段（禁 await）+ 异步段（1.5s 超时）」，所有 `chrome.*` Promise 套 `withTimeout` 兜底 |

### 缺陷 7 详解（真机 P0，值得单独记住）

**表象**：扩展加载后判定条、输入输出区、按钮一应俱全，看起来完全正常，
但**输入区点不动、粘贴不进**，第一步就卡住。

**根因**：`AppController.init()` 中 `await loadPrefs()` 排在 `createEditor()` **之前**。
在企业托管 Chrome 环境下，`chrome.storage` 的 Promise 可能既不 resolve 也不 reject，
await 永不返回 → 编辑器永远创建不出来。由于页面骨架是纯 HTML，
**布局看起来完全加载正常**，误导性极强。

**为什么自动化测不出来**：jsdom 里 `chrome.storage` 不存在，
`loadPrefs()` 直接走 `if (!chrome?.storage?.local) return {}` 同步返回，
await 立刻完成 —— 这条路径在 jsdom 里根本不会发生。

**复现方法**：注入一个「永不 settle 的 chrome.storage」，
对照组 `cmCount: 0 / statusMsg: ""`，与用户截图逐像素吻合。

**回归防线**：`tests/acceptance/ui-init-hang.test.ts`（3 例）。
已做反向验证 —— 改回 buggy 写法后 3 例全红，恢复后全绿。

**通用教训**：任何 `chrome.*` Promise 都必须假设它可能永不 settle，
UI 初始化路径上的 await 一律要有超时兜底。

另：TypeScript 严格模式错误从 39 个降至 0（`die()` 的 `never` 未推断、缺失 chrome 类型声明等）。

## 七、如何使用产物

1. 下载 `json-dialect-dist-v1.0.0.zip` 并解压
2. Chrome 打开 `chrome://extensions/`，开启右上角「开发者模式」
3. 点「加载已解压的扩展程序」，选择解压后的目录（该目录下须能直接看到 `manifest.json`）
4. 点击扩展图标即可使用

**注意**：必须选择包含 `manifest.json` 的那一层目录，否则 Chrome 会拒绝加载。
