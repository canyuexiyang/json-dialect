## 一、修订条目

### 1.1 FR-A13（输出方向规则）—— 改写

| | 内容 |
|---|---|
| **v1.2 原文** | 在「来源 = Python 字面量」状态下输出标准 JSON；在「来源 = 标准 JSON / Java 转义 / Map」状态下输出 Python 字面量。 |
| **v1.3 新文** | 系统输出方向**由目标格式选择器决定**。目标为「自动」时，沿用原有推导规则（来源 = Python → JSON；其余 → Python）；用户显式指定目标时，按指定目标序列化，且**该选择不得影响来源格式的判定**。 |
| **理由** | 原规则把输出写死成来源的函数，导致"粘 JSON 只想格式化"被强制转 Python、US-17 无法实现。 |

### 1.2 FR-F2（界面布局）—— 五段改六段

| | 内容 |
|---|---|
| **v1.2 原文** | 界面应采用上下五段布局：顶部判定条 / 输入区 / 分隔条 / 输出区 / 底部操作栏。 |
| **v1.3 新文** | 界面应采用上下六段布局：**功能 tab 条** / 判定条 / 输入区 / 分隔条 / 输出区 / 底部操作栏。tab 条位于最上方，顺序固定为 **① 格式化 · ② 转义 · ③ 转换**。弹窗形态下 tab 使用紧凑样式（高度 ≤ 32px）；放大页不受此约束。 |
| **理由** | tab 化后功能入口需前置；720×600 弹窗纵向空间紧张，须约束 tab 高度。 |

### 1.3 FR-E7 / FR-E7a（下载扩展名）—— 映射扩展

| | 内容 |
|---|---|
| **v1.2 原文** | 输出标准 JSON → `.json`；输出 Python 字面量 → `.py`。 |
| **v1.3 新文** | 输出标准 JSON → `.json`；输出 Python 字面量 → `.py`；**输出 Java 转义字符串 → `.txt`**。按钮文案同步（「下载 .json」/「下载 .py」/「下载 .txt」）。 |
| **理由** | Java 转义串不是合法 Java 源文件，存成 `.java` 会误导后续使用（沿用 Q5 的同一判据）。 |

### 1.4 US-17（Python → Java 转义）—— P2 升 P0

| | 内容 |
|---|---|
| **v1.2** | P2「未来考虑」，Q8 标注"本期不做"。 |
| **v1.3** | **升为 P0**，纳入本期。由 FR-A17（目标解耦）+ FR-A18（Java 转义输出）共同实现。 |
| **理由** | 目标解耦后实现成本大幅下降（复用 IR，约 40 行），且"贴进 Java 代码"是真实高频场景。 |

### 1.5 AC-31 —— 同步修订

新增一条子项：目标 = Java 转义串时，下载文件名后缀为 `.txt`，按钮文案为「下载 .txt」。

## 二、新增需求条目

### 2.1 FR-A｜转换引擎（目标格式解耦）

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| **FR-A17** | **[O]** | P0 | 在具备目标格式选择器时，系统应允许用户独立指定**目标格式**，且该选择**不得**影响来源格式的判定。可选目标为标准 JSON / Python 字面量 / Java 转义字符串三种。 |
| **FR-A18** | **[U]** | P0 | 系统应支持输出 **Java 转义字符串**：对序列化结果执行 JSON 字符串编码，产出可直接贴进 Java 代码字符串常量的形态。 |
| **FR-A19** | **[X]** | P0 | 若目标格式与来源格式相同，系统应执行**同语言规范化**（解析后重新序列化），等价于"格式化"语义，且**不得**改变任何值的类型与内容。 |

> **FR-A17 的排除项**：`Map.toString()` **不得**作为可选目标。
> 理由：Map 输出有损（类型信息丢失、字符串无引号、嵌套歧义），
> 会产出"看起来对但语义已变"的文本，违背 FR-D11 的"宁可明确失败"精神。
> 故目标矩阵为 **4 来源 × 3 目标 = 12 种组合**。

> **FR-A19 的定位**：它是「格式化 tab」的内核基础 —— 让"同语言进出"成为一等公民，
> 不必再靠"骗来源格式"绕过。

### 2.2 FR-D｜容错与报错（静默错误修复）

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| **FR-D11** | **[X]** | P0 | 若主干结构解析完成后仍存在未被消费的 token（尾部残留），系统应**报错**并给出残留首 token 的行列位置，**不得**静默忽略。错误文案应区分「尾部存在多余内容」与「检测到多个并列值（如 JSON Lines），本工具一次只处理一个值」。 |
| **FR-D12** | **[U]** | P0 | 修正记录的类型应与实际修正动作一致。系统**不得**用「删除末尾多余逗号」标记「忽略残留内容」这类动作。 |
| **FR-D13** | **[X]** | P1 | 若解析失败且检测到输入在主干结构之前存在疑似日志前缀（时间戳、日志级别、线程名等），系统应在报错信息中提供**一键入口**「剥离日志前缀后重试」；点击后截去前缀并重新解析。 |
| **FR-D14** | **[E]** | P1 | 当用户点击「剥离日志前缀后重试」时，系统应在修正记录或提示条中**显式列出被剥离的前缀文本**，确保该操作可追溯。 |

> **FR-D11 与定位的一致性**（重要，防止实施时被误读为违背"容错优先"）：
> 「能救就救」针对的是**同一个值内部的语法残缺**（缺括号、多逗号、单引号）；
> 而**丢弃额外的值**不是修复，是**静默丢数据**。
> PRD §10 R2 明确写着「静默错误比报错更危险」—— FR-D11/D12 正是 R2 的落地。

> **FR-D13 实现要点**（已实测验证，勿改用正则）：
> 复用已有 lexer 的 Token 流，定位第一个**结构起始 token**（`{` 或 `[`），
> 取其 `start` 偏移截取原文。Token 自带 `start/line/col`，剥离位置天然精确。
> **不要**用正则匹配时间戳 —— 实测会漏剥 `ERROR com.foo.Bar - {...}` 的 logger 名。

> **FR-D13 附属**：BOM（`\uFEFF`）应在 lexer 层剥离，避免带 BOM 的 JSON 被误判为 Java 转义格式。

### 2.3 FR-I｜转义 tab（新增章节）

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| **FR-I1** | **[E]** | P0 | 在转义 tab 中，系统应对整段文本执行转义或反转义，**不得**尝试解析其结构。 |
| **FR-I2** | **[U]** | P0 | 转义风格应至少支持：JSON 字符串转义、Java 字符串转义、URL 百分号编码、Base64。每种均支持**双向**。 |
| **FR-I3** | **[X]** | P0 | 若反转义失败（如非法 Base64），系统应报错并说明原因，**不得**返回部分结果或空串。 |
| **FR-I4** | **[U]** | P0 | Base64 编解码应**始终按 UTF-8 字节序列**处理。 |

> **FR-I4 实测硬约束（不写进需求实现时必踩）**：
> 原生 `btoa('中文')` 抛 `InvalidCharacterError`（只接受 Latin-1）。
> 必须走 `TextEncoder → btoa` 与 `atob → TextDecoder`。
> 实测验证：`TextEncoder+btoa('中文')` = `5Lit5paH`，可逆。

> **架构注记**：转义 tab 是**纯字符串**通道（文本 → 文本），**不经过 IR**，
> 与转换/格式化 tab（IR → 文本）本质不同。实施时应作为独立链路，
> **不得**硬塞进 `convert()`。

### 2.3b FR-I｜转义方向（v1.4 新增，结果测试反馈）

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| **FR-I5** | **[U]** | P0 | 转义 tab 应始终提供**显式的方向二选一**：「去除转义」与「增加转义」，常驻可见并标明当前选中项。方向**不得**藏进按钮的隐式翻转。默认方向为「增加转义」，且该选择应持久化（历史偏好覆盖默认值）。 |
| **FR-I6** | **[E]** | P0 | 当用户执行「去除转义」时，若整段文本被一对**配对的外层引号**包裹，系统应先剥离该对引号再反转义，并在状态条**显式提示**「已自动去除外层引号」。**不得**剥离中间存在未转义同种引号的文本。 |
| **FR-I7** | **[U]** | P0 | 任一风格下，「增加转义」的结果再执行「去除转义」应还原为原文（往返一致）。 |

> **FR-I5 的理由（实测缺陷）**：v1.1.0 把方向做成了底部按钮的隐式翻转 ——
> 按钮只显示当前方向（「编码」/「解码」），用户点一下才知道它其实是切换器。
> 结果测试时用户反馈**「没有去除转义的选项」**。这不是功能缺失，是**可见性缺失**，
> 但用户体验上等价。故改为常驻二选一 + 底部按钮明确写出「反向会变成什么」。

> **FR-I6 的理由（真实复制场景）**：从 Java / JSON 代码里复制出来的字符串常量
> **自带外层引号**，如 `"{\"a\":1}"`。不剥壳会得到 `"{"a":1}"` —— 外层引号残留，
> 用户还得手删。剥壳**不是**解析结构（FR-I1 禁止的），只是脱掉「常量外壳」。
>
> **安全判据（必须实现）**：不能只比较首尾字符。要扫描一遍确认中间的
> 同种引号**都被反斜杠转义**，否则 `a" + "b` 会被误判。
> 实测四种风格都安全：url 编码后 `"` → `%22`，base64 字母表不含 `"`。

### 2.4 FR-J｜扩展图标

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| **FR-J1** | **[U]** | P1 | manifest 应声明 `icons`（16 / 48 / 128），使扩展在工具栏与扩展管理页显示自有图标。 |

**约束**：图标必须是**本地 PNG 资源**，不得引用外部 URL（AC-36 无外部 CDN）。
建议用本地脚本绘制（纯色 + 符号），不引入外部素材，保住零网络。

### 2.5 FR-K｜格式化 tab（新增章节）

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| **FR-K1** | **[S]** | P0 | 在格式化 tab 中，系统应默认以**严格模式**解析输入：任何语法偏差均**报错**并给出行列，**不得**自动修复。 |
| **FR-K2** | **[O]** | P1 | 在具备「容错」开关时，用户可切换为容错模式，此时按转换 tab 的宽松规则处理，并在修正记录中逐条列出改动。 |
| **FR-K3** | **[U]** | P1 | 格式化 tab 的容错档位选择应持久化，作为独立偏好项，与「转换 tab 的目标格式」互不干扰。 |
| **FR-K4** | **[O]** | P1 | 格式化 tab 应提供「美化 / 压缩」二选一，复用现有 compact 逻辑，仅去除**字符串外部**的结构空白（FR-A14）。 |

> **FR-K1 的理由**：美化场景下用户要的是**确定性** —— 告诉我在哪行出错，
> 而不是自作主张帮我改数据。这与转换 tab 的"能救就救"是两种不同的心智，
> 用不同容错档位反而让各自更清晰。FR-K2 提供开关，避免把"脏输入想弄整齐"堵死。

### 2.6 FR-L｜tab 框架（新增章节）

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| **FR-L1** | **[U]** | P0 | 界面应始终提供三个功能 tab，顺序固定为 **① 格式化 · ② 转义 · ③ 转换**。 |
| **FR-L2** | **[U]** | P0 | **默认选中「格式化」**（格式化为 v1.1 主路径）。 |
| **FR-L3** | **[S]** | P1 | 在无历史偏好时（首次安装 / 数据清理后），系统应选中「格式化」；存在历史偏好时，应选中上次离开时的 tab。**默认值的优先级低于历史偏好。** |
| **FR-L4** | **[U]** | P1 | 三个 tab **共享**内核（lexer / 四个 parser / IR / 序列化器），但**不共享**输入内容、来源锁定与类型覆盖。 |

> **FR-L2 的依据**：格式化使用频次高于转换，是真实主路径。
> v1.0 将其排在后面属历史包袱（当时只有转换功能），v1.1 予以修正。
> 因属"修正主路径"而非"妥协"，**不设**"转换去哪了"的首次使用提示。

> **FR-L3 的两条需求容易打架**，必须写清优先级：默认格式化是**初始值**，
> tab 记忆是**覆盖值**。否则"记住上次"会把默认值架空。

> **FR-L4 的理由**：跨 tab 共享输入会造成"我在格式化 tab 改了东西，
> 回转换 tab 发现也变了"，属于惊喜而非便利。

## 三、新增验收标准（AC-53 ～ AC-70）

### 3.1 静默错误修复（F1/F2/F3）

| # | 方式 | 期望 |
|---|---|---|
| **AC-53** | 输入 `2024-01-01 12:00:00 INFO {"a":1}` | **报错**并给出行列；**不得**输出 `2024-01-01` 且状态为 `fixed` |
| **AC-54** | 输入 `{"a":1}\n{"b":2}`（JSON Lines） | **报错**提示"检测到多个并列值"；**不得**静默只出第一个 |
| **AC-55** | 输入 `{"a":1} garbage` | 报错「尾部存在多余内容」，给出 `garbage` 起始行列 |
| **AC-56** | 上述任一报错场景检查修正记录 | 修正记录**不得**出现「删除末尾多余逗号」（该文案只能用于真实逗号场景） |
| **AC-57** | 输入 `\uFEFF{"a":1}`（带 BOM） | 判定为**标准 JSON**，不得误判为 Java 转义字符串 |

### 3.2 日志前缀一键剥离（FR-D13/D14）

| # | 方式 | 期望 |
|---|---|---|
| **AC-58** | 输入 `2024-01-01 12:00:00 INFO {"a":1}` 报错后 | 错误信息中提供「剥离日志前缀后重试」入口 |
| **AC-59** | 点击该入口 | 输出 `{'a': 1}`，且**明确显示被剥离的前缀文本** `2024-01-01 12:00:00 INFO ` |
| **AC-60** | 输入 `2024-01-01 12:00:00 ERROR com.foo.Bar - {"a":1}` 剥离后 | 正确解析出 `{'a': 1}`（logger 名被一并剥离） |
| **AC-61** | 输入 `{"a":1}`（无前缀） | **不得**触发剥离入口（不得误伤合法输入） |

### 3.5b 转义方向（v1.4 新增，FR-I5～I7）

| # | 方式 | 期望 |
|---|---|---|
| **AC-74** | 打开转义 tab | 顶部可见「去除转义 / 增加转义」二选一，默认选中**增加转义**，选中态清晰 |

| **AC-80** | 选择方向后关闭再打开 | 记住上次选择（历史偏好覆盖默认值） |
