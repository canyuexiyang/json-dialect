## 0. 一句话结论

**用 `chrome.sidePanel`（侧边栏）承载主界面，popup 降级为「快速取用入口」。**
这是唯一同时满足「常驻不关」+「不占标签页」+「官方支持」的方案。
但项目当前 `.app` 硬编码 `width: 720px`，与侧边栏 320–360px 的物理上限**直接冲突**，
必须先做布局响应化改造——这是本次的主要工作量，不是 API 接入。

---

## 1. 问题定性：这是机制，不是 bug

当前 manifest 声明：

```json
"action": { "default_popup": "popup.html" }
```

Chrome 对 `default_popup` 的生命周期有硬性规定：

> popup 渲染器在页面**失去焦点**的那一刻被销毁。

所以「切到 B 标签 → popup 消失 → 切回 A 标签 → 内容没了」是**规范定义的必然行为**，
任何代码都拦不住。`docs/03-研发` 里记录的坑 14（组件 `display` 盖掉 `[hidden]`）
和坑 9（`await` 拖死初始化）都是真 bug，但**与本问题无关**。

> ⚠️ 需求方常有的误解：以为"我加个全局变量保存一下就行"。
> 真实情况是 popup 文档被销毁后，JS 堆上的变量一起没了。
> 唯一能在 popup 关闭后存活的是 `chrome.storage`（session/local），
> 而本项目 FR-H4 明确规定**输入内容零落盘**，只允许写界面偏好。
> 这条约束与"常驻"需求天然冲突，见 §5 风险 R1。

**推论：想在 popup 形态下解决"常驻"，唯一出路是改承载形态，不是修状态管理。**

## 2. 候选方案全景对比

| 维度 | A. 侧边栏 sidePanel | B. 独立标签页 | C. 独立窗口 popup | D. DevTools 面板 | E. popup+状态持久化 |
|---|---|---|---|---|---|
| **切换标签页后存活** | ✅ 文档存活 | ✅ | ✅ | ⚠️ 随 DevTools 关闭 | ❌ 仍被销毁 |
| **不占标签页位置** | ✅ | ❌ 占用一个 tab | ✅ | ✅ | ✅ |
| **宽度上限** | ❌ 320–360px | ✅ 整窗 | ✅ 自由（可调） | ✅ 整窗 | — |
| **需用户手动关闭** | ✅ | ✅ 手动关 tab | ✅ | ✅ | ❌ |
| **需额外权限** | `sidePanel` | 无（现 `window.open` 已有） | `windows`/`tabs` | `devtools_page` | 无 |
| **需开 DevTools** | ❌ | ❌ | ❌ | ✅ 必须 F12 | ❌ |
| **代码改动量** | 中高 | 低（已实现） | 中 | 中 | 高 |
| **符合项目"零落盘"** | ✅ | ✅ | ✅ | ✅ | ❌ 内容要落盘 |
| **Firefox 兼容** | ❌ 无此 API | ✅ | ✅ | ✅ | ✅ |

**淘汰说明：**

- **B（独立标签页）** —— 项目**已经实现了**（顶栏「放大」按钮 → `app.html`）。
  零新增成本就能获得"常驻不关"。但它占用一个标签页位置，
  用户抱怨的"切标签就丢"问题虽然解决了，却换来"我的标签栏多了一个图标"的新负担。
  **适合作为长文本大改场景，不适合做默认形态。**
- **C（独立窗口）** —— 视觉上最理想（大小自由、始终置顶），但需要 `windows` 权限，
  且窗口焦点切换规则复杂（失焦是否自动隐藏由 OS 决定，行为不可控）。
  与项目「仅 `storage` 权限」的隐私承诺冲突，**性价比低**。
- **D（DevTools 面板）** —— 必须开着 F12，对非开发者是灾难。
  本项目用户画像恰恰是开发者，但仍是过度设计，**淘汰**。
- **E（popup + 状态持久化）** —— 唯一被**直接否掉**的方案，理由见 §5 R1。

## 3. 推荐方案：侧边栏为主 + 放大页兜底

### 3.1 交互形态

```
用户点扩展图标
    ↓
侧边栏展开（chrome.sidePanel.open，窗口级，跨 tab 存活）
    ↓
用户切到 B 标签干别的事 → 侧边栏隐藏，但文档存活
    ↓
切回 A 标签 → 侧边栏原样回来，内容还在
    ↓
用户点侧边栏 X / 点扩展图标 → 真正关闭
```

**关键设计点：面板必须用 `windowId` 打开，不能用 `tabId`。**

- `tabId` 作用域：面板只属于那一个 tab，tab 一换就没了 —— **这是常见误用**
- `windowId` 作用域：面板属于整个窗口，切换 tab 时自动隐藏再自动恢复
  （与 Chrome 自带的「书签/阅读列表」面板行为一致）

### 3.2 入口设计（双入口，各司其职）

| 入口 | 行为 | 场景 |
|---|---|---|
| 侧边栏下拉菜单 | 直接选中面板 | 主路径，常驻使用 |
| 扩展图标单击 | `sidePanel.open({windowId})` | 不知道有侧边栏的用户 |
| 「放大」按钮（保留） | `window.open` 整页 | 长文本、大段改写 |
| 快捷键（建议新增） | `_execute_side_panel` / `_execute_action` | 键盘流用户 |

> **注意入口冲突**：`action.default_popup` 与 `setPanelBehavior({openPanelOnActionClick:true})`
> **互斥**。若采用侧边栏为主，`default_popup` 需从 manifest 移除，
> 改为在 service worker 里 `onInstalled` + `onStartup` 调 `setPanelBehavior`。
> 若想保留 popup 作为快速入口，则改用 `chrome.sidePanel.open()`（Chrome 116+，
> **必须在用户手势回调内调用**）从 popup 按钮跳转。

## 4. 落地前必须解决的两个硬问题

### 🔴 P0-1：布局宽度冲突（主要工作量）

`src/ui/styles.css:206` 硬编码：

```css
.app {
  width: 720px;
  height: 600px;
}
```

而 Chrome 侧边栏**物理最小宽度 320px**（Chromium 源码 `kSidePanelMinWidth`），
默认约 360px。**720px 塞不进去，会被压缩或溢出。**

改造方向：

- `.app` 宽度改为 `width: 100%; min-width: 0`，高度 `100vh`
- `.app--large`（整页）保留现有 `100vw/100vh`
- 顶部条在 <420px 下需要**换行或折叠**：现有 tab 条 + 品牌名 + 放大按钮
  横向排列，360px 必然溢出
- 判定条（来源 ▸ 目标 + 锁定 badge + 重置按钮）同理需窄屏化
- 底部工具栏 5 个按钮在 360px 下需考虑收进「更多」菜单
- 竖向 splitter（输入/输出高度分隔）在纯竖长空间里其实**比 popup 更合适**，可保留

> 建议：这不是"改个宽度"就完事，**必须真机在 320 / 360 / 500px 三档验收**。
> 本项目历史教训（坑 14、坑 15）都是「测试全绿但真机错位」，务必留出真机目测环节。

### 🟡 P0-2：`sidePanel` 是新增权限

当前 manifest 仅 `["storage"]`，零 host 权限——这是项目的**隐私核心卖点**，
也是 v1.2 隐私扫描的验收基础（AC-37）。

`sidePanel` 权限的实际情况：

- 属于**非 host 权限**，不申请 `activeTab` / `<all_urls>`
- Chrome 官方明示：侧边栏**无需 host 权限即可展示 UI**，
  这是「对用户重大的隐私保护改进，同时减少安装时的权限警告数」
- 不会削弱 FR-H4「输入内容零落盘」——面板文档内照样不写 storage

**但它确实让 manifest 从 1 条权限变成 2 条。** 这属于对外可见的承诺变更，
需要拍板并在 README / 商店描述中同步说明（不能让用户以为这是零权限扩展）。

## 5. 风险清单

| 编号 | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| R1 | **与 FR-H4 冲突**：若最终选择"popup 存内容以保住数据"，直接违反零落盘承诺 | 🔴 高 | 已在 §2 淘汰 E 方案。侧边栏方案下输入内容随文档存活，**不落盘即可满足需求**，冲突自然消解 |
| R2 | Firefox / Safari 无 `sidePanel` API | 🟡 中 | 项目是纯 Chrome MV3 扩展（README 已声明），暂无跨浏览器计划。若将来需要，侧边栏作为**渐进增强**，popup 保留兜底 |
| R3 | 窄屏布局回归 | 🔴 高 | §4 P0-1；真机三档验收 + 截图对比 |
| R4 | 侧边栏与 Chrome 自带面板（书签/阅读列表）**互斥，同一位置只能显示一个** | 🟢 低 | 面板顶部有下拉可切换，用户可接受；需在文档中说明 |
| R5 | 侧边栏宽度**不跨会话持久化**（用户拖动的宽度重启后还原） | 🟢 低 | Chrome 行为，不可控。默认宽度下布局已可用（见 R3 改造） |
| R6 | `sidePanel.close()` 需 Chrome 141+ | 🟢 低 | 低版本降级：隐藏关闭按钮，让用户用 Chrome 自带的面板 X |

## 6. 待拍板的三个问题

1. **要不要接受 manifest 加 `sidePanel` 权限？**（隐私叙事 vs 常驻体验）
2. **popup 是保留还是移除？** 保留 = 双入口更友好但代码多一份分叉；移除 = 干净但失去"随手取用"
3. **窄屏（<420px）布局是重排还是折叠？** 重排更充分利用空间，改动大；折叠快，但信息层级变浅

## 7. 建议的落地顺序

| 阶段 | 内容 | 产出 |
|---|---|---|
| **S1 布局改造**（不碰 manifest） | `.app` 响应式化，popup / 整页 / 侧边栏三态共用一套 DOM | CSS + 三档真机截图 |
| **S2 快捷键**（不碰 manifest） | 加 `_execute_action`，零成本提升 reopen 速度 | manifest `commands` |
| **S3 侧边栏接入**（拍板后） | 加 `sidePanel` 权限 + service worker + 入口互斥处理 | manifest + sw.js |
| **S4 文档同步** | README / PRD / 隐私声明同步 | 文档 |

> S1、S2 无论 S3 是否拍板都值得做——它们是纯增益，且不引入权限变更。
> 建议先落地 S1+S2，实际用几天再决定要不要 S3。

## 附：关键 API 速查

```jsonc
// manifest.json
{
  "permissions": ["storage", "sidePanel"],
  "side_panel": { "default_path": "sidepanel.html" },
  "action": { "default_title": "JSON Dialect" },  // 注意：无 default_popup
  "commands": {
    "_execute_side_panel": {                      // Chrome 116+
      "suggested_key": { "default": "Ctrl+Shift+J", "mac": "Command+Shift+J" }
    }
  }
}
```

```js
// service worker —— 必须在模块顶层同步注册（MV3 worker 30s 即被回收）
chrome.runtime.onInstalled.addListener(() => {
  chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true }).catch(() => {});
});
chrome.runtime.onStartup.addListener(() => {
  chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true }).catch(() => {});
});

// 从 popup / 内容脚本 / 快捷键打开 —— 必须在用户手势回调内
chrome.sidePanel.open({ windowId });   // ✅ 窗口级，跨 tab 存活
// chrome.sidePanel.open({ tabId });  // ❌ tab 级，切换 tab 即失效
```
