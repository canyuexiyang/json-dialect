## 零、为什么要改（定性结论，不是偏好问题）

v1.2 用 `action.default_popup` 承载主界面。Chrome 对popup 的生命周期有硬性规定：
**渲染器在页面失去焦点的那一刻被销毁**。

所以「切到 B 标签 → popup 消失 → 切回 A 标签 → 内容没了」是**规范定义的必然行为**，
任何代码都拦不住 —— 这不是 bug，是机制。

| 承载形态 | 切标签后 | 手动关闭 | 宽度 | 结论 |
|---|---|---|---|---|
| popup | ❌ 销毁 | 自动 | 720px 固定 | 淘汰 |
| **sidePanel** | ✅ 文档存活 | ✅ | 320–360px | **采用** |
| 独立标签页 | ✅ | ✅ 手动关 tab | 整窗 | **采用**（已实现，强化） |

**关键约束**：侧边栏宽度物理下限 320px（Chromium `kSidePanelMinWidth`），
与v1.2 写死的 `.app { width: 720px }` 正面冲突。**这是本次主要工作量，不是 API 接入。**

## 二、新增需求（承载形态，编号沿用 S = Surface）

### FR-S1 主形态为侧边栏 【U】

> 系统应以 `chrome.sidePanel` 作为主界面承载形态，manifest 声明 `side_panel.default_path` 指向侧边栏页面。

**理由**：唯一同时满足「跨标签存活」+「不占标签页位置」+「官方支持」的方案。

**约束**：

- `default_popup` 必须从 manifest 删除 —— popup 优先级更高，会顶掉面板行为
- 因此**必须新增 service worker**（无 popup 时若无 `action.onClicked` 监听，
  点图标将完全无反应）
- worker 只注册面板行为，不承载业务逻辑

### FR-S2 面板以窗口为作用域 【U】

> 系统打开侧边栏时，面板作用域必须为窗口（`windowId`），而非标签页（`tabId`）。

**理由**：这是本次需求最易写错的一点。`tabId` 会让面板只属于那一个 tab，
切换即失效 —— **症状与 v1.2 的 popup 完全一样**，会被误判为「重构没生效」。

### FR-S3 界面须在 320px 宽度下完整可用 【U】

> 系统的主界面在 320 / 360 / 500px 三档宽度下，所有可操作控件必须完整可见且可点击，不得出现横向滚动。

**理由**：侧边栏最窄 320px 是物理下限。v1.2 的 `.app` 写死 720×600 + `overflow:hidden`，
在侧边栏下会把「复制」「下载」「标签页」按钮**直接裁掉** ——
其中「标签页」被裁意味着用户**无法进入大空间形态**，等于功能缺失。

**约束**：本条**无法由单元测试验证**（jsdom 不做布局计算），必须真机三档目测。

## 三、修订条目

| 条目 | 原表述 | 修订后 | 依据 |
|---|---|---|---|
| **FR-F6** | 点击「放大」按钮 → 独立标签页 | 按钮**文案改为「标签页」** | 「放大」描述的是动作，「标签页」描述的是形态。新用户点之前就该知道点完会发生什么 |
| **FR-H4** | 输入内容零落盘 | **措辞补充，承诺不变** | 见下方专门澄清 |
| **FR-H7** | 跨页会话态走 `storage.session`，读后即清 | 适用范围明确为「侧边栏 → 标签页」的**一次性交接** | 避免被理解为「侧边栏持续写会话」 |

### FR-H4 澄清（本次最易误解的点）

> **侧边栏文档长期存活 ≠ 内容落盘。**

输入内容能跨标签页存活，是因为**文档没有被销毁**，
不是因为它被写进了任何存储。FR-H4 的承诺**完全不变**：

| 存储 | 写什么 | 何时清 |
|---|---|---|
| `storage.local` | 界面偏好（tab 记忆 / 缩进档位 / 分隔比例） | 不清 |
| `storage.session` | 「侧边栏 → 标签页」的一次性交接包 | **读后立即清除** |
| 输入 / 输出内容 | **什么都不写** | —— |

任何把会话内容写进 `storage.local` 来实现「常驻」的实现，都违反 FR-H4。

## 五、Non-goals（明确不做，防止范围蔓延）

- ❌ 不引入 `tabs` / `windows` / `activeTab` / `scripting` 权限
- ❌ 不碰 `chrome.tabs.create` 禁令（AC-49）—— 标签页形态继续 `window.open`
- ❌ **不动 `src/core/` 任何一行** —— lexer / parser / serializer 与承载形态完全无关
- ❌ 不做跨浏览器（Firefox / Safari 无 `sidePanel` API）
- ❌ 不引入 React / Vue 等框架，保持零框架
- ❌ 不改「一次 tokenize + strict/lenient 开关」等核心架构约束

## 九、真机反馈修订（2026-10-08 深夜，发布前）

v1.3.0 产物真机实测后用户反馈两个问题，补充两条条目（已并入 PRD 正文）。

| 条目 | 定性 | 处置 |
|---|---|---|
| **FR-S4 / AC-87** 点「标签页」后侧边栏不关，屏幕两个实例 | **真 bug**：只做了「开」没做「关」 | 优先 `chrome.sidePanel.close({windowId})`（**Chrome 141+ 才有**，须先判存在再调，否则同步抛错连兜底都跳过）→ 兜底 `window.close()`。`windowId` 走 `chrome.windows.getCurrent()` —— **该方法不需要任何 manifest 权限**（只有读 `Window.tabs` 才要 `tabs`），FR-H2 权限承诺不变 |
| **FR-S5 / AC-88** 侧边栏太窄，想要默认 1/3 窗口宽 | **Chrome 硬限制，非 bug** | `sidePanel.PanelOptions` 只有 `enabled`/`path`/`tabId`，**没有 width**；宽度默认约 360px、最小约 320px，只能用户拖边缘。「按窗口比例自适应」**无法实现**。已在界面内以一次性引导条（`prefs.hintWidth`，界面偏好不违反 FR-H4）如实告知，并引导升级到标签页形态 |

> 两条均已写入 `docs/01-需求/PRD.md` 正文：FR-S4 见 §6，AC-87/88 见 §8.10，
> 宽度限制以 FR-S5「不可实现，仅记录」形式留档 —— **避免后人重复尝试**。
