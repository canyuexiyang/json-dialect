## 零、先说结论

调研下来有一个反直觉的发现：

> **我们不缺"JSON 工具箱"的能力，缺的是把已经做对的事做完。**

竞品调研给出的高频功能清单（格式化/压缩/校验/排序/树视图/Diff/JSONPath），
我们 **PRD 的 §3 非目标里已经逐条论证过为什么不做**（NG6/NG7/NG8）。
那些不是遗漏，是当初主动砍掉的。盲目补进去只会稀释"格式翻译器"的定位。

但实测暴露了 **3 个真实缺陷 + 1 个结构性限制**，这些是 v1.0 没做对、
且竞品调研根本不会告诉我们的东西：

| # | 发现 | 性质 | 严重度 |
|---|---|---|---|
| **F1** | 日志前缀文本导致**整段数据被静默吃掉** | 静默错误 | 🔴 P0 |
| **F2** | JSON Lines 多行输入**静默丢弃后续对象** | 静默错误 | 🔴 P0 |
| **F3** | 带 BOM 的 JSON 被误判为 Java 转义格式 | 误判（可恢复） | 🟡 P1 |
| **F4** | 输出方向由来源格式**硬编码推导**，无法自由选目标 | 结构性限制 | 🟠 P1（最大增量） |

其中 **F1/F2 是"输出看起来正常但实际是错的"**，这恰好是 PRD §10 R2 点名的
最高危风险类型：**静默错误比报错更危险**。建议优先修。

## 一、我们现在的真实能力边界（实测结论）

用 `convert()` 实测 4 种输入方向：

| 输入 | 判定来源 | 输出方向 | 输出 |
|---|---|---|---|
| `{"a":1,"b":{"c":[1,2,3]}}` | json | **python** | `{'a': 1, 'b': {...}}` |
| `{'a':1,'b':[1,2]}` | python | **json** | `{"a": 1, "b": [1, 2]}` |
| `{name=张三, age=18}` | map | **python** | `{'name': '张三', 'age': 18}` |
| `"{\"k\":\"v\"}"` | java | **python** | `{'k': 'v'}` |

**输出方向 = f(来源格式)**，写死在 `types.ts::outputLangFor()`：
`python → JSON`，其余三种 → `Python`。

### 1.1 已经做得比竞品好的地方（别自我怀疑）

实测确认这些是真优势，市面上很少见：

| 能力 | 实测结果 | 市面稀缺度 |
|---|---|---|
| 精度无损 | `12345678901234567890` 原样输出；`1e5` 保持 `1e5` | **高**（浏览器 `JSON.parse` 必丢精度） |
| `Map.toString()` 解析 | `{url=https://a.com/?x=1&y=2}` → 正确（值内 `=` 不误切） | **极高**（几乎无工具支持） |
| 嵌套 Map | `{list=[{b=1},{c=2}]}` 正确 | 极高 |
| 引号智能选择 | `'say \'hi\''` → `"say 'hi'"`（不傻转单引号） | 中高 |
| 容错修复可追溯 | 逐条列出行列 + 改动前后 | 高 |
| 纯本地零网络 | manifest 仅 `storage` | 中高（本地不稀奇，但"零网零盘 + 翻译器"组合稀缺） |
| 全格式回退 | 判定错会自动尝试其他 3 种 | 高 |

**结论**：`四向方言翻译 + 容错 + 精度无损` 这个组合在市面上近乎空白。
这是护城河，v1.1 应该**加深它**，而不是去追编辑器能力。

## 三、实测发现的缺陷（本节是本文最有价值的部分）

### 🔴 F1：日志前缀导致整段数据被静默吃掉

```
输入：2024-01-01 12:00:00 INFO {"a":1}
输出：2024-01-01
状态：fixed      ← 报的是"已修复"，不是错误！
```

**期望**：`{'a': 1}` 或至少明确报错。

**危害**：用户从日志里粘出一行，得到一个看似正常的输出，
实际整段 payload 全丢了，而且界面还显示"已自动修正 N 处"——
这会让用户**以为工具正常工作了**。典型的静默错误。

**为什么发生**：容错层把 `2024-01-01` 当成一个合法值解析成功，
后面的文本被丢弃。修复逻辑过于激进。

---

### 🔴 F2：JSON Lines 静默丢弃后续对象

```
输入：{"a":1}\n{"b":2}
输出：{'a': 1}      ← 只剩第一个
状态：fixed
```

**期望**：要么报错提示"检测到多个并列值"，要么包成数组 `[{...},{...}]`。

**危害**：同 F1。NDJSON / JSON Lines 在日志场景非常常见，
粘进去丢数据且无任何提示。

**注**：PRD §12 Q4 明确写了「整体判定，不分段」，
理由是避免误伤 JSON 数组。**这条决策本身没错**（粘 `[{...},{...}]` 不能拆），
但 `\n` 分隔的**裸并列值**是另一种情况，应该在解析出多余 token 时报错，
而不是静默截断。

---

### 🟡 F3：带 BOM 的 JSON 被误判为 Java 转义格式

```
输入：\uFEFF{"a":1}
判定：java     ← 应为 json
输出：{'a': 1}  ← 结果碰巧对
```

**危害**：结果虽对，但判定错了。BOM 在 Windows 环境/Excel 导出的 JSON 里很常见。
判定错会导致**修正记录与回退提示误导用户**。

**修法**：lexer 首字符剥离 BOM（`\uFEFF`）即可，成本极低。

---

### 🟠 F4：输出方向由来源硬编码，无法自由选择目标格式

```ts
// src/core/types.ts
export function outputLangFor(src: SourceFormat): OutputLang {
  return src === 'python' ? 'json' : 'python';
}
```

**走不通的真实场景**：

| 场景 | 现状 | 用户现在怎么办 |
|---|---|---|
| 粘一段 JSON 只想**格式化** | 被强制转成 Python | 去别处格式化，或骗来源格式 |
| JSON → **Java 转义串**（贴进 Java 代码） | 无此方向 | 手工加反斜杠（PRD US-17 挂了） |
| Python → Python（只修语法不换语言） | 不可能 | 无解 |
| Map → JSON | 只能先转 Python 再转 | 两步 |

**当前唯一绕过方式**：手动把来源锁成 `python` 去"骗"它输出 JSON ——
这是个 hack，而且输出方向仍不可控。

**改造方案**（核心增量）：

1. `ConvertOptions` 增加 `target?: SourceFormat`（默认 `auto` = 沿用现有推导）
2. `buildResult()` 里 `outLang` 由 `target` 决定，不再由 `source` 推导
3. 新增 `toJavaEsc()` 序列化器（复用 IR，约 40 行）
4. UI：判定条右侧加一个「目标格式」选择器，默认「自动」
5. `outputLang` 类型从 `'json'|'python'` 扩展为 `'json'|'python'|'java'`

**成本估算**：核心改造集中在 `types.ts` + `index.ts`（`outputLang` 全项目仅
出现于 3 个文件），加一个新序列化器。**不碰 lexer、不碰四个 parser**。
这是"已有 IR 内核"带来的杠杆 —— 架构当初的设计在这里兑现了。

**收益**：4×4 = 16 种组合全可达，一次性解决 US-17 和"只想格式化"两个老诉求。

## 五、建议的 v1.1 范围（三档，供你选）

### 方案 A：只修缺陷（最小） 🔴 推荐起步

- F1 日志前缀静默丢数据
- F2 JSON Lines 静默截断
- F3 BOM 误判

**理由**：这三条都是"输出看着对但实际错"，直接违背 PRD 的核心承诺
（G2 核心规则零误差 + R2 静默错误最危险）。**它们会让你在未来某次
联调时复制到一个错的数而不自知** —— 这正是当初做这个工具要避免的事。
成本极低（不动架构），收益极高（消除信任隐患）。

### 方案 B：修缺陷 + 目标格式解耦（推荐）

- 方案 A 全部
- F4 目标格式选择器（4×4 矩阵）

**理由**：F4 是唯一能带来**质变**的增量。它把工具从
「4 个固定方向的翻译器」变成「4×4 格式转换矩阵」，
一次性解决"只想格式化"和"JSON→Java 代码"两个被挂起的老诉求（US-17）。
且因为 IR 内核已经存在，成本远低于从零做。

### 方案 C：B + 体验补齐

- 方案 B 全部
- C1 输出可编辑、C3 示例按钮、C4 图标
