## 二、缺陷修复（Q1 / Q2）

### 🔴 根因已定位到代码行

F1 与 F2 **同一个根因**，都在 `src/core/parse/engine.ts:405-410`：

```ts
// 尾部残留：strict 模式报错；宽松模式尝试忽略
if (!c.eof()) {
  const rest = c.peek()!;
  if (strict) die('unexpected_token', rest, '尾部存在多余内容');
  marks.push(mk('trailing_comma', rest, rest.raw, ''));   // ← 三个问题在这
}
```

1. **宽松模式无条件忽略尾部残留**，不报错 —— 数据就这么没了。
2. **修正记录类型打错**：用 `trailing_comma`（"删除末尾多余逗号"）去标记
   实际是"忽略了一整段内容"。
3. `lexer.ts:27` 其实**早已定义了正确的类型 `tail_ignored`**
   （"忽略主干结构之后的残留内容"），但从未被使用。

**实测证据**（`convert()` 实跑）：

| 输入 | 实际输出 | 状态 | 修正记录文案 |
|---|---|---|---|
| `2024-01-01 12:00:00 INFO {"a":1}` | `2024-01-01` | fixed | 「删除末尾多余逗号」← 谎报 |
| `{"a":1}\n{"b":2}` | `{'a': 1}` | fixed | 「删除末尾多余逗号」← 谎报 |
| `{"a":1} garbage` | `{'a': 1}` | fixed | 「删除末尾多余逗号」← 谎报 |
| `{"a":1},{"b":2}` | `{'a': 1}` | fixed | 「删除末尾多余逗号」← 谎报 |

四种情况**全部静默丢数据 + 谎报修正类型**。这是 v1.0 最严重的缺陷。

### 修复需求

| ID | 类型 | 需求描述 |
|---|---|---|
| **FR-D11** | **[X]** | 若主干结构解析完成后仍存在未被消费的 token（尾部残留），则系统应**报错**并给出残留首 token 的行列位置，**不得**静默忽略。错误文案应区分「尾部存在多余内容」与「检测到多个并列值（如 JSON Lines），本工具一次只处理一个值」。 |
| **FR-D12** | **[U]** | 修正记录的类型应与实际修正动作一致。系统**不得**用「删除末尾多余逗号」标记「忽略残留内容」这类动作。 |

> **与「容错优先」定位的一致性**：FR-D11 看似违背定位，实际不是。
> 「能救就救」针对的是**同一个值内部的语法残缺**（缺括号、多逗号、单引号）；
> 而**丢弃额外的值**不是修复，是**静默丢数据**。
> PRD §10 R2 明确写着「静默错误比报错更危险」—— 这两条正是 R2 的落地。

**配套**：`ErrorKind` 新增 `trailing_content` / `multiple_values`；
`fixLog.ts` 启用已有的 `tail_ignored` 用于真正可忽略的场景（见 O-2）。

## 三、目标格式解耦（Q3 / Q4）

### 3.1 现状

```ts
// src/core/types.ts
export function outputLangFor(src: SourceFormat): OutputLang {
  return src === 'python' ? 'json' : 'python';
}
```

输出方向 = f(来源)，写死。US-17（JSON→Java 转义）因此挂了整个 v1.0。

### 3.2 变更需求

| ID | 类型 | 需求描述 |
|---|---|---|
| **FR-A17** | **[O]** | 在具备目标格式选择器时，系统应允许用户独立指定**目标格式**，且目标格式的选择**不得**影响来源格式的判定。 |
| **FR-A18** | **[U]** | 系统应支持输出 **Java 转义字符串**：对目标文本执行 JSON 字符串编码，产出可直接贴进 Java 代码字符串常量的形态。 |
| **FR-A19** | **[X]** | 若目标格式与来源格式相同，则系统应执行**同语言规范化**（解析后重新序列化），等价于「格式化」语义，且**不得**改变任何值的类型与内容。 |
| **修订 FR-A13** | — | 原「输出方向由来源决定」改为「由目标格式决定；目标为自动(默认)时沿用原有推导」。 |

> **FR-A19 是「格式化 tab」的内核基础** —— 它让"同语言进出"成为一等公民，
> 不必再靠"骗来源格式"绕过。

### 3.3 实现路径（已验证）

- `OutputLang` 从 `'json' | 'python'` 扩展为 `'json' | 'python' | 'java'`
- `ConvertOptions` 增加 `target?: SourceFormat | 'auto'`，默认 `'auto'`（行为不变）
- `toJavaEsc()` = `toJson()` 输出 + `encodeJsonString()` 二次编码 —— **已实测验证可行**
- **不碰 lexer、不碰四个 parser**
- `outputLang` 全项目仅 3 处引用：`core/index.ts`、`core/types.ts`、`ui/controller.ts`

### 3.4 4×4 矩阵里建议关掉的一格

`→ Map.toString()` 是**有损**的（类型信息丢失、字符串无引号、嵌套歧义）。
建议 **Map 不作为可选目标**，矩阵实际为 4×3 = 12 种组合。
→ 需你确认（O-7）。

## 四、功能 tab 划分（N4）

### 4.1 关键判断：tab 不能按「目标格式」切

你的参考图是「先选功能，下面的框跟着变」。这里有个陷阱：

> **若按目标格式切 tab（→JSON / →Python / →Java），等于把目标选择器变成了 tab，
> 那么"只想格式化"时用户仍不知道该点哪个**，而且会和 F4 的目标选择器**打架**。

### 4.2 最终方案：按「用户意图」切三个 tab（顺序已确认）

| 顺序 | Tab | 心智 | 输入 | 输出 | 来源识别 | 容错档位 |
|---|---|---|---|---|---|---|
| **①** | **格式化** ⭐默认 | 同语言弄整齐 | 四种方言 | 与输入同格式 | ✅ 自动 | **严格**（默认）+ 可切容错 |
| **②** | **转义** | 纯字符串处理 | 任意文本 | 转义/反转义 | — | — |
| **③** | **转换** | 跨语言翻译 | 四种方言 | 目标选择器决定 | ✅ 自动 + 可锁定 | **宽松**（能救就救） |

**默认选中「格式化」（O-1 / 第三轮已确认）**，理由与你的判断一致：
多数人打开插件的高频动作是"把一段文本弄整齐"，跨语言翻译是次频动作。

**格式化 tab 严格模式的理由**（O-1 已确认）：

转换 tab 的灵魂是"能救就救"。但**美化场景下用户要的是确定性** ——
我想把这段 JSON 弄整齐，你告诉我第 3 行少个括号就够了，不要自作主张帮我改数据。
两个 tab 用不同容错档位，反而让各自心智更清晰。

| ID | 类型 | 需求描述 |
|---|---|---|
| **FR-K1** | **[S]** | 在格式化 tab 中，系统应默认以**严格模式**解析输入：任何语法偏差均**报错**并给出行列，**不得**自动修复。 |
| **FR-K2** | **[O]** | 在具备「容错」开关时，用户可将其切换为容错模式，此时系统按转换 tab 的宽松规则处理，并在修正记录中逐条列出改动。 |
| **FR-K3** | **[U]** | 格式化 tab 的容错档位选择应持久化，并作为独立偏好项与「转换 tab 的目标格式」互不干扰。 |

### 4.3 三个 tab 共享内核，不共享状态

- **共享**：lexer / 四个 parser / IR / 三个序列化器 —— **零新增解析成本**
- **不共享**：输入框内容、来源锁定、类型覆盖
  - 理由：跨 tab 共享输入会造成"我在格式化 tab 改了东西，回转换 tab 发现也变了"，
    属于惊喜而非便利。

> ⚠️ **但「默认选中格式化」带来一个待确认问题**：见下方 O-11。

## 五、转义 / 去转义（N3）

### 5.1 认知纠正：这是「纯字符串」能力，不是第五种方言

前三个 tab 都是 **IR → 文本**（结构化）。转义 tab 是 **文本 → 文本**（非结构化），
**根本不走 IR**。这是它必须独立成 tab 的原因，也决定了它不能硬塞进 `convert()`。

### 5.2 需求

| ID | 类型 | 需求描述 |
|---|---|---|
| **FR-I1** | **[E]** | 在转义 tab 中，当用户输入文本并选择目标转义风格时，系统应对整段文本执行转义或反转义，**不得**尝试解析其结构。 |
| **FR-I2** | **[U]** | 转义风格应至少支持：JSON 字符串转义、Java 字符串转义、URL 百分号编码、Base64。每种均支持**双向**。 |
| **FR-I3** | **[X]** | 若反转义失败（如非法 Base64），系统应报错并说明原因，**不得**返回部分结果或空串。 |
| **FR-I4** | **[U]** | Base64 编解码应**始终按 UTF-8 字节序列**处理。 |

> **FR-I4 是实测得来的硬约束，不写进需求实现时必踩**：
> 原生 `btoa('中文')` 直接抛 `InvalidCharacterError`（只接受 Latin-1）。
> 必须走 `TextEncoder → btoa` 与 `atob → TextDecoder`。
> 实测已验证：`TextEncoder+btoa('中文')` = `5Lit5paH`，可逆。

### 5.3 与现有能力的关系

- **不冲突**：Java 转义作为**输入方言**已存在（FR-C2，走 IR）；
  转义 tab 是**纯文本**通道。入口不同、语义不同。
- **互补**：粘 `"{\"k\":\"v\"}"` → 转换 tab 解析成结构；
  粘一段普通文本想加反斜杠 → 转义 tab。

## 八、你可能还没想到的点（补充）

### ✅ O-1：格式化 tab 容错档位 —— **已确认**

**决策**：严格模式 + 提供「严格 / 容错」小开关，**默认严格**。

### ✅ O-2：日志前缀一键剥离 —— **已确认采纳**

**决策**：转换 tab 报错（安全优先），错误信息里带一键入口「剥离日志前缀后重试」。

#### 实现方案（已做技术验证，两版方案的取舍）

我试了两种剥离策略，**正则方案不可靠**，建议用基于 lexer 的方案：

| 方案 | 结果 |
|---|---|
| ❌ **纯正则**匹配时间戳+级别 | `ERROR com.foo.Bar - {...}` 这类 logger 名**漏剥**；`[http-nio-8080]` 方括号段处理不稳 |
| ✅ **复用 lexer Token 流**定位结构起始 | 8 个测试样本中 6 个正确剥离，且不误伤 `{"a":1}`、`[1,2,3]`、纯文本 |

**推荐实现**（FR-D13）：

1. 对输入执行 `lex()`（已有，零成本）
2. 在 Token 流中定位第一个**结构起始 token**（`{` 或 `[`）
3. 若该 token 前有内容 → 判定为"疑似日志前缀"，报错并给出一键入口
4. 用户点击 → 从该 token 的 `start` 偏移截取原文，重新转换

**这个方案的好处**：复用已有 Token 流（每个 token 自带 `start/line/col`），
**不需要新写一套前缀识别正则**，也天然拿到了精确的剥离位置。
剩下 2 个未覆盖样本（方括号包裹的时间戳）属于边缘形态，
可留给"手动锁定来源 + 手动删除"兜底。

| ID | 类型 | 需求描述 |
|---|---|---|
| **FR-D13** | **[X]** | 若解析失败且检测到输入文本在主干结构之前存在疑似日志前缀（时间戳、日志级别、线程名等），则系统应在报错信息中提供**一键入口**「剥离日志前缀后重试」；用户点击后，系统应截去前缀部分并重新执行解析，**并明确告知用户已剥离的内容片段**。 |
| **FR-D14** | **[E]** | 当用户点击「剥离日志前缀后重试」时，系统应在修正记录或提示条中**显式列出被剥离的前缀文本**，确保该操作可追溯（与 FR-D4/D5 一致的"改动可见"原则）。 |

> FR-D14 是我补的：**剥离了什么必须让用户看见**，否则又变成另一种静默行为。

### 🟢 O-6：转换 tab 里，目标选择器放哪？

建议放**判定条右侧**，与来源选择器对称：
`[来源: 自动 ▾] → [目标: 自动 ▾]`
"来源 → 目标"一眼可读，比塞进底部工具栏好。

### ✅ O-7：`→ Map.toString()` 作为可选目标 —— **已确认不允许**

**决策**：接受建议。目标格式可选 **JSON / Python / Java 转义** 三种，
`Map.toString()` **仅作为来源**不作为目标。矩阵为 **4×3 = 12 种组合**。

理由：Map 输出有损（类型信息丢失、字符串无引号、嵌套歧义），
作为目标会产出"看起来对但语义已变"的文本 —— 违背 Q1 的"宁可明确失败"精神。

### 🟢 O-8：F3（BOM 误判）别忘了

提案里的 F3 你没单独提，但它是已确认缺陷。
**建议一并修**（lexer 剥 BOM，成本极低）。默认纳入，除非你反对。

### 🟢 O-9：放大页需同步 tab 状态

`SessionState` 当前只有 `input / source / locked / compact / overrides`（已核实）。
tab 化后需增加 `tab` 与 `target` 两个字段，否则放大后回到默认 tab。

### 🟢 O-10：样本集需扩充

现有 41 组样本全是四方言，无日志类输入 —— **F1/F2 正是因此漏网**。
建议补 ≥10 条日志类样本作为回归防线。

## 八（续）. 由「默认选中格式化」新引出的问题

### ✅ O-11：默认 tab 变更 —— **已确认：默认格式化，不加首次提示**

**你的决策及理由**：

> v1.0 的主路径确实是转换，但**转换的使用量小于格式化**，
> 因此 v1.1 把格式化列为主路径，默认选中。

**这个理由改变了问题性质** —— 它不是"要不要迁就老习惯"的取舍，而是：

| | 说明 |
|---|---|
| 事实 | 格式化使用频次 > 转换使用频次 |
| 结论 | 格式化**才是真实主路径**，v1.0 把它排在后面是历史包袱（当时只有转换功能） |
| 动作 | v1.1 修正主路径，默认选中格式化 |

既然是**修正**而非**妥协**，我之前建议的「首次使用提示」就**不需要了** ——
给一个符合真实使用频次的设计加道歉式提示，是自相矛盾的。

| 决策项 | 结论 |
|---|---|
| 默认 tab | **① 格式化** |
| 首次提示 | **不加** |
| O-5 tab 记忆 | **保留**（仍记住上次离开的 tab，但默认回格式化） |

> 补充一条实现约束：**「默认」与「记住上次」的优先级**要写清楚 ——
> 首次安装 / 清理数据后 → 格式化；此后 → 上次离开的 tab。
> 否则"记住上次"会把默认值架空，两个需求互相打架。

### 🟢 O-12：格式化 tab 的「严格」档位，要不要同时提供「压缩」？

格式化 tab 的语义是"同格式美化/压缩"。既然有美化（缩进），
配一个压缩（单行）是自然的（v1.0 已有 `btnCompact`，只是挂在底部工具栏）。
**建议**：格式化 tab 提供「美化 / 压缩」二选一，复用现有 compact 逻辑，零成本。
→ 按建议执行，除非你反对。
