| 方案 | 结果 |
|---|---|
| ❌ 纯正则匹配时间戳+级别 | `ERROR com.foo.Bar - {...}` 的 logger 名漏剥 |

# 追加：v1.1.1 转义方向重设计（2026-09-22 结果测试后）

## 起因

结果测试反馈：**「转义 tab 下没有去除转义的选项」**。

排查后发现内核**有** decode 能力，方向切换藏在底部按钮的隐式翻转里 ——
按钮只显示当前方向（「编码」/「解码」），用户点一下才知道它其实是切换器。
**这不是功能缺失，是可见性缺失，但用户体验上等价。**

## FR-I6 外层引号剥离的设计推演

实测发现从代码复制出来的 Java/JSON 常量**自带外层引号**：
```
"{\"a\":1}"  --decode-->  "{"a":1}"     ← v1.1.0：外层引号残留，用户还得手删
             --decode-->  {"a":1}       ← v1.1.1：先剥壳再反转义
```

**安全判据（不能只比较首尾字符）**：扫描一遍确认中间的同种引号**都被反斜杠转义**，
否则 `a" + "b` 会被误判成带外层引号。已加用例 AC-76 守住。

**为什么四种风格都安全**：url 编码后 `"` → `%22`，base64 字母表不含 `"` ——
这两种风格的输出里不可能出现裸引号，所以首尾同种引号一定是复制带来的外壳。
（初版我只给 json/java 剥，`"5Lit5paH"` 直接报错，实测后才放宽到全部风格。）
