## 一、背景与问题陈述

### 1.1 问题

**同时写 Python 和与 Java 后端联调的开发者，每天要反复把一段数据结构在两种"长得像但不兼容"的字面量之间手工改写。**

具体痛点（来自需求访谈）：

| 痛点 | 现状做法 | 代价 |
|---|---|---|
| Python `dict` 的 repr 无法直接给 Java 用 | 手工把单引号改双引号、`True`→`true`、`None`→`null` | 每次 1–5 分钟，长对象极易漏改，改完还是非法 JSON |
| 后端日志里粘出来的是 `Map.toString()`（`{name=张三, age=18}`） | 手工补引号、补冒号 | 完全没有标准工具能直接吃这个格式 |
| Java 代码里复制出来的是转义过的字符串（`{\"name\": \"x\"}`） | 手工删反斜杠 | 机械劳动，长文本基本靠编辑器正则碰运气 |
| 从日志/聊天记录里粘出来的片段常常不完整（缺括号、带注释、末尾多逗号） | 先修语法再转换，或干脆放弃 | 现有在线工具一律直接报错，不给任何定位 |

### 1.2 现有方案的缺口

- **在线 JSON 格式化工具 / `JSON.parse`**：严格模式，`单引号`、`True`、`末尾逗号`、`Map.toString()` 全部拒收，且报错只说 "Unexpected token"，不给行列或只给字符偏移量。
- **通用文本替换（编辑器正则）**：无法区分字符串内部与外部，`"it's"`、`{\"n\": \"a=b\"}` 这类必然误伤。
- **Python `json.dumps` / `ast.literal_eval`**：能解决方向一的一半，但需要开终端、贴进脚本、处理中文转义，且完全不覆盖 Java 侧三种输入形态。

**不做这件事的代价**：这件事每天发生、单次耗时不长但频次高，长期是持续的隐性时间税；且手工改写引入的静默错误（漏改一个 `True`、多删一个反斜杠）会在联调时才暴露，排查成本远高于转换成本。

### 1.3 一句话产品定义

> **一个能在浏览器里就地完成 Python 字面量与 Java/标准 JSON 互转的小工具，容错优先，能救就救。**

**核心定位判断**：这是**格式翻译器**，不是**严格 JSON 校验器**。用户要的是"把眼前这段文本变成能被目标语言直接吃掉的形态"，而不是"验证它是否规范"。因此**容错的优先级高于严格性**——这一条是所有解析相关需求的裁决依据，遇到"该报错还是该修复"的两可情形，一律优先修复。

## 二、目标（Goals）

| # | 目标 | 衡量方式 | 类型 |
|---|---|---|---|
| G1 | **粘贴即出结果**：粘贴后无需点任何按钮即得到可用输出 | 从粘贴到输出稳定 ≤ 500ms；30 条真实样本中无需手动点击「转换」的比例 = 100% | 用户 |
| G2 | **核心规则零误差**：单引号、`True/False/None`、`null/true/false` 的互转 100% 准确 | 核心规则专项用例 100% 通过（见 §8.1） | 用户 |
| G3 | **畸形输入能救就救**：常见残缺/噪声输入自动修复而非报错 | 10 条畸形样本中 ≥ 8 条自动修复成功，且每处修复均可追溯 | 用户 |
| G4 | **救不了时精确定位**：不可修复的输入给出行列级错误定位 | 5 条不可修复样本 100% 给出正确行号与列号 | 用户 |
| G5 | **零学习成本、零数据外泄**：打开即用，全部计算在本地完成 | 无网络请求、无 host 权限、无埋点（代码级可验证，见 FR-H） | 用户 + 安全 |

**非用户目标的说明**：本产品为个人自用，不设 DAU / 留存 / 变现类业务目标。§9 的指标设计完全围绕"这工具是否真的帮我省了时间"。

## 三、非目标（Non-Goals）

明确不做，防止实现期范围蔓延：

| # | 非目标 | 不做的原因 |
|---|---|---|
| NG1 | **历史记录 / 转换记录回溯** | 用户明确未选；且历史记录需要持久化用户数据，与"零数据留存"的隐私设计直接冲突 |
| NG2 | **自定义快捷键** | 用户明确未选；弹窗形态下焦点管理复杂，收益低于成本 |
| NG3 | **右键菜单 / 选中文本直接转换** | 用户明确选择弹窗形态；右键菜单需 `activeTab`/`contextMenus` 权限，与最小权限原则冲突 |
| NG4 | **严格校验模式开关** | 用户明确未选。产品定位是"翻译器不是校验器"，加严格模式会引入两套互斥心智模型 |
| NG5 | **任何形式的网络请求 / 云端能力 / AI 辅助转换** | 与纯本地隐私设计根本冲突；且用户粘贴的可能是生产数据 |
| NG6 | **多格式扩展（YAML / XML / Protobuf / CSV）** | 超出"Python ↔ Java JSON"这一具体痛点；每加一种格式都会指数级放大解析器复杂度 |
| NG7 | **JSON Schema 校验 / JSONPath 查询 / Diff 对比** | 这些是"JSON 工具箱"的能力，不是本产品的定位。做进去会把弹窗撑成 IDE |
| NG8 | **缩进风格、键名排序、中文转义的可配置开关** | 用户已明确选定固定默认值（2 空格 / 不排序 / 不转义）。加开关是给自用工具增加无谓的决策负担 |

## 四、用户画像与使用场景

本产品只有**一个真实用户**（开发者本人），但这个人会在**两顶帽子之间切换**，两顶帽子对应两个方向的转换需求。用角色区分有助于独立检验两个方向是否都做完整。

### 4.1 角色 A：写 Python 的开发者（Python → JSON）

- 手上是 Python 脚本/调试器里打印出来的 `dict` / `list` repr
- 需要把它变成能贴进 API 调试工具、Java 侧 mock 数据、配置文件的内容
- 典型触发：调接口前构造请求体、把调试结果发给人看

### 4.2 角色 B：与 Java 后端联调的开发者（JSON → Python）

- 手上是后端日志、接口文档、Java 代码里的字符串常量、`Map.toString()` 输出
- 需要把它变成能直接贴进 Python 的 `dict` 字面量
- 典型触发：复现一个线上请求、把 Java 侧返回体转成 Python 测试数据

### 4.3 场景清单

| # | 场景 | 方向 | 输入特征 | 频率 |
|---|---|---|---|---|
| S1 | 调试器里打印的 Python dict 转标准 JSON | A | 干净但非标准（单引号 + True/None） | 高 |
| S2 | 从聊天/文档里粘来的 Python 片段，带 `#` 注释、末尾逗号 | A | 脏 | 中 |
| S3 | 后端日志里的 `Map.toString()` 转 Python dict | B | 非 JSON 语法 | 中 |
| S4 | Java 代码里复制的转义字符串转 Python dict | B | 含 `\"` | 中 |
| S5 | 标准 JSON 接口返回体转 Python dict | B | 干净合法 | 高 |
| S6 | 大段 JSON（数百行、深嵌套）转换 | 双向 | 体积大，考验性能 | 低 |
| S7 | 结构被截断（缺右括号）时的定位排查 | 双向 | 不可修复 | 低 |

## 五、用户故事

按优先级排序。格式为 `作为 [角色]，我希望 [能力]，以便 [价值]`。

### P0 —— 核心链路

- **US-01**｜作为角色 A，我希望粘贴 Python 字面量后立刻得到标准 JSON，以便我不用手工改引号和 `True/None`。
- **US-02**｜作为角色 B，我希望粘贴标准 JSON 后立刻得到 Python 字面量，以便我能直接贴进 Python 代码。
- **US-03**｜作为角色 B，我希望粘贴 `Map.toString()` 输出也能被正确解析，以便我不用手工补引号和冒号。
- **US-04**｜作为角色 B，我希望粘贴 Java 转义过的字符串能自动反转义，以便我不用手工删反斜杠。
- **US-05**｜作为用户，我希望一键把输出复制到剪贴板，以便我的主要动作就是"粘贴—复制"两步。
- **US-06**｜作为用户，我希望看到工具识别出的是哪种来源格式，并在识别错时能一键切换，以便我不必为了让它认对而先手工改文本。
- **US-07**｜作为用户，我希望输入不完整时工具能自动修复而不是报错，以便我处理从日志里截断粘出来的片段。
- **US-08**｜作为用户，我希望真修不了时能看到第几行第几列出错、为什么错，以便我知道该去改哪里。

### P1 —— 显著提效

- **US-09**｜作为用户，我希望在 `Map.toString()` 模式下能手动把某个值改成字符串/数字/布尔/null，以便自动推断猜错时我能纠正（例如订单号 `0012` 必须保持字符串）。
- **US-10**｜作为用户，我希望看到"已自动修正 N 处"并能展开看每一处改了什么，以便我信任输出、知道它被改过。
- **US-11**｜作为用户，我希望能把输出在"美化"和"压缩成一行"之间切换，以便分别用于阅读和贴进单行字段。
- **US-12**｜作为用户，我希望有一个放大按钮，以便处理大段文本时不受弹窗尺寸限制。
- **US-13**｜作为用户，我希望界面跟随系统深浅色，以便夜间使用不刺眼。
- **US-14**｜作为用户，我希望处理几百行嵌套结构时不卡顿，以便它不会在我最需要的时候拖后腿。
- **US-15**｜作为用户，我希望能把结果导出成文件，以便存档或传给他人。

### P2 —— 未来考虑（本期不做，仅确保架构不堵死）

- **US-16**｜作为用户，我希望输出区偶尔可以手动微调后再复制，以便处理个别推断错误。
- **US-17**｜作为角色 A，我希望直接输出 Java 字符串字面量形式（转义过的 JSON），以便直接贴进 Java 代码。

## 六、功能需求

需求条目采用 **EARS** 句式编写，五类标签含义：

| 标签 | 句式 | 含义 |
|---|---|---|
| **[U]** Ubiquitous | 系统应始终…… | 无条件的恒定约束 |
| **[E]** Event-driven | 当[事件]时，系统应…… | 由事件触发的行为 |
| **[X]** Unwanted | 若[异常条件]，则系统应…… | 异常/故障处理 |
| **[S]** State-driven | 在[状态]期间，系统应…… | 特定状态下的持续行为 |
| **[O]** Optional | 在具备[特性]时，系统应…… | 可选/条件性功能 |

优先级：**P0** = 缺了就不能解决核心问题；**P1** = 核心链路可用但体验明显受损；**P2** = 本期不做。

### FR-A｜转换引擎核心规则（P0）

> 转换引擎的全部规则应实现为**纯函数、独立模块、不依赖任何浏览器 API**，以便脱离浏览器跑单元测试。这是本项目最重要的架构约束——核心难点在解析器而不在界面，规则正确性必须能被独立验证。

**方向一：Python 字面量 → 标准 JSON**

| ID | 类型 | 需求描述 |
|---|---|---|
| FR-A1 | **[U]** | 系统应始终将 Python 裸字面量 `True` 转换为 JSON `true`。 |
| FR-A2 | **[U]** | 系统应始终将 Python 裸字面量 `False` 转换为 JSON `false`。 |
| FR-A3 | **[U]** | 系统应始终将 Python 裸字面量 `None` 转换为 JSON `null`。 |
| FR-A4 | **[U]** | 系统应始终将单引号包裹的字符串转换为双引号包裹，并按 JSON 规范转义其内部字符。 |
| FR-A5 | **[U]** | 系统应始终将 Python 元组 `(…)` 转换为 JSON 数组 `[…]`。 |
| FR-A6 | **[U]** | 系统应始终保持对象键的原始顺序，不得排序、**去重**或重排。**修订（G-5）**：重复键亦应原样保留全部条目（忠实于输入），但系统应在修正提示条中提示「存在重复键 N 个，目标语言求值时后者将覆盖前者」。 |
| FR-A7 | **[U]** | 系统应始终原样输出非 ASCII 字符（含中文），不得转换为 `\uXXXX` 形式。 |

> **FR-A1–A4 是用户明确点名的核心需求，必须 100% 准确**，任何容错逻辑不得覆盖或改写这四条的结果。

**方向二：标准 JSON → Python 字面量**

| ID | 类型 | 需求描述 |
|---|---|---|
| FR-A8 | **[U]** | 系统应始终将 `true` → `True`、`false` → `False`、`null` → `None`。 |
| FR-A9 | **[U]** | 系统应始终按 §7.2「引号选择算法」决定 Python 侧字符串的引号形式，**不得**执行简单的双引号→单引号字符替换。**已确认（Q1）：含单引号且不含双引号时使用双引号。** |
| FR-A10 | **[U]** | 系统应始终使输出的 Python 字面量可被 `ast.literal_eval` 正确求值（作为跨验证标准）。 |

**双向通用**

| ID | 类型 | 需求描述 |
|---|---|---|
| FR-A11 | **[U]** | 系统应始终以**原始 token 字符串**透传数字，不得经由 JavaScript `Number` 做数值转换，不得改写为科学计数法，不得补零、去零或做数值归一化。 |
| FR-A12 | **[X]** | 若字符串值中包含控制字符（换行、制表、回车等），则系统应按目标语言的转义语法正确转义，且不得破坏字符串边界。转义对照表见 **§7.7**。 |
| FR-A13 | **[S]** | **修订（v1.3）**：系统输出方向**由目标格式选择器决定**。目标为「自动」时，沿用原有推导规则（来源 = Python → JSON；其余 → Python）；用户显式指定目标时，按指定目标序列化，且**该选择不得影响来源格式的判定**。 |
| FR-A14 | **[U]** | 系统应始终保留字符串内部的空白与内容原貌，压缩操作（FR-E3）仅影响结构空白，不影响字符串内部。 |
| FR-A15 | **[X]** | **新增（G-2，原 Q7）**：若 Python 源中出现 `NaN` / `Infinity` / `-Infinity`（Python `repr` 会产出，但非合法 JSON），则系统应将其转换为 `null`，并在修正提示条中逐条列出该转换。 |
| FR-A16 | **[X]** | **新增（G-2，原 Q9）**：若 Python 源中出现非字符串键（如 `{1: 'a'}`、元组键 `(1,2): 'x'`），则系统应将该键转换为字符串后输出（`{1:'a'}` → `{"1":"a"}`；元组键取其字面量文本），并在修正提示条中逐条列出。 |
| FR-A17 | **[O]** | **新增（v1.3）**：在具备目标格式选择器时，系统应允许用户独立指定**目标格式**，且该选择**不得**影响来源格式的判定。可选目标为标准 JSON / Python 字面量 / Java 转义字符串三种。 |
| FR-A18 | **[U]** | **新增（v1.3）**：系统应支持输出 **Java 转义字符串**：对序列化结果执行 JSON 字符串编码，产出可直接贴进 Java 代码字符串常量的形态。 |
| FR-A19 | **[X]** | **新增（v1.3）**：若目标格式与来源格式相同，系统应执行**同语言规范化**（解析后重新序列化），等价于"格式化"语义，且**不得**改变任何值的类型与内容。 |

> **FR-A13 已按 v1.3 改写**：输出方向**由目标格式选择器决定**。目标为「自动」时沿用原有推导规则；用户显式指定目标时按指定目标序列化，且不得影响来源判定。
> 原写法把输出写死成来源的函数，导致"粘 JSON 只想格式化"被强制转 Python、US-17 无法实现。

> **FR-A17 的排除项**：`Map.toString()` **不得**作为可选目标（Map 输出有损，会产出"看起来对但语义已变"的文本）。故目标矩阵为 **4 来源 × 3 目标 = 12 种组合**。

> **FR-A11 是精度保障的关键**：把数字当字符串透传，超大整数（如 `12345678901234567890`）、`1.0`、`1e5` 全部原样保留，且实现成本为零。见 Q2。
>
> **FR-A15 / FR-A16 的设计原则**：这两类输入都无法在目标语言中无损表达。选择「转换 + 显式提示」而非「静默丢弃」或「静默透传产出非法结果」——前者丢信息，后者产出不可用的输出。见 §12 Q7 / Q9，本期固化。

### FR-B｜来源格式自动识别与手动覆盖（P0）

> 上游文档只写了"转换方向自动识别"，未定义判定规则。本节补齐判定算法（§7.1）与覆盖优先级，这是弹窗能否"开箱即用"的关键。

| ID | 类型 | 需求描述 |
|---|---|---|
| FR-B1 | **[U]** | 系统应始终在四个候选来源格式中判定：① Python 字面量 ② 标准 JSON ③ Java 转义字符串 ④ `Map.toString()`。 |
| FR-B2 | **[E]** | 当输入区文本发生变化（粘贴、编辑、清空）且文本非空时，系统应在 200ms 防抖后自动执行来源判定并重新转换。 |
| FR-B3 | **[U]** | 系统应始终按 §7.1 打分算法判定来源格式，打分仅统计**字符串字面量外部**的信号，不得把字符串内容中的 `True`、`null`、`=` 计入。**修订（C-2）**：打分器应复用解析器 lexer 产出的 Token 流，不得另写一套引号状态机；每类信号的计分应设置次数上限（见 §7.1）。 |
| FR-B4 | **[X]** | 若打分结果为平局或未命中任何有效信号，则系统应默认判定为「标准 JSON」。 |
| FR-B5 | **[E]** | 当用户在顶部判定条手动选择来源格式时，系统应立即以该格式重新解析并转换，该选择应覆盖自动判定结果。 |
| FR-B6 | **[S]** | 在用户已手动选择来源格式的状态下，系统应持续沿用该选择，直到用户再次切换或清空输入区。 |
| FR-B7 | **[E]** | 当输入区被清空时，系统应清除手动选择标记，恢复自动判定。 |
| FR-B8 | **[X]** | （**已被 FR-B11 泛化，本条保留以说明 JSON 特例的最优先回退顺序**）若自动判定为「标准 JSON」且第 1 层解析失败，则**在用户未手动锁定来源格式的前提下**，系统应先依次尝试「Java 转义字符串」与「Map.toString()」解析，任一成功即更新判定结果；两者均失败后仍按 FR-B11 尝试其余格式。 |
| FR-B9 | **[U]** | 顶部判定条应始终显示当前生效的来源格式，并以视觉标记区分「自动判定」与「手动锁定」两种状态。 |
| FR-B10 | **[E]** | 当用户手动切换来源格式后，系统应在判定条旁显示「重置为自动」入口；点击后清除锁定并重新自动判定。 |
| FR-B11 | **[X]** | **新增（G-1）**：若当前判定的来源格式三层解析均失败，且用户未手动锁定来源格式，则系统应依次尝试**其余三种**来源格式（不局限于 FR-B8 的「JSON → Java 转义 / Map」链路）；任一成功即更新判定结果，并在提示条标注「已按 X 格式解析」。 |

> **FR-B11 的理由**：原 FR-B8 的回退链只覆盖「判定为 JSON 时失败」一种情况，判定为 Python 或 Map 失败时不会尝试其他格式，用户粘错格式就彻底救不回来——这与"能救就救"的产品定位直接冲突。实现成本极低：四种 parser 消费的是同一份 Token 流，回退无需重新扫描（见评审报告 §5.2）。

> **FR-B4 的平局裁决理由**：两种误判都可恢复（一键切换即可），但判定为 JSON 来源时输出的是 Python 字面量，即使判错，输出仍然是人类可读的结构化文本；判定为 Python 来源时输出的是 JSON，判错同样可读。选择 JSON 作为平局默认值是因为它是更常见的粘贴来源。

### FR-C｜Java 侧三种输入形态与 Map 类型推断（P0 / P1）

| ID | 类型 | 优先级 | 需求描述 |
|---|---|---|---|
| FR-C1 | **[U]** | P0 | 系统应始终支持解析标准 JSON 输入。 |
| FR-C2 | **[E]** | P0 | 当输入文本呈现 Java 字符串转义特征（整段被双引号包裹且内部双引号被 `\"` 转义）时，系统应先执行反转义（`\"`→`"`、`\\`→`\`、`\n`→换行、`\t`→制表）再解析。 |
| FR-C3 | **[E]** | P0 | 当输入文本呈现 `key=value` 分隔且不构成合法 JSON 时，系统应以 `Map.toString()` 解析器解析。 |
| FR-C4 | **[U]** | P0 | `Map.toString()` 解析器应始终按「当前括号深度为 1 处的**第一个** `=`」切分键与值。 |
| FR-C5 | **[U]** | P0 | `Map.toString()` 值的类型推断规则应始终为：纯数字 → 数字；`true`/`false`（忽略大小写）→ 布尔；`null`（忽略大小写）→ `null`；其余 → 字符串。 |

| FR-C7 | **[E]** | P0 | 当用户在类型下拉框中更改某值的类型时，系统应立即重渲染输出，且**不得**触发对输入文本的重新解析。 |
| FR-C8 | **[U]** | P0 | 手动类型覆盖应始终按「值在结果结构中的路径」记录；输入文本变化时，系统应按路径尝试重建覆盖，路径已不存在则丢弃该项。 |
| FR-C9 | **[S]** | P1 | 在存在手动类型覆盖的状态下，系统应对被覆盖的值显示视觉标记（边框或角标），明确区分"推断值"与"人工指定值"。 |
| FR-C10 | **[E]** | P1 | 当用户点击「清除覆盖」时，系统应清空全部手动覆盖并恢复自动推断结果。 |
| FR-C11 | **[S]** | P1 | 在 `Map.toString()` 模式下，若推断出的值数量 > 50，系统应将行内下拉降级为输出区下方的「类型调整面板」列表形式（避免行内控件过多导致渲染卡顿）。 |
| FR-C12 | **[U]** | P1 | `Map.toString()` 解析器应支持嵌套结构（如 `{user={name=张三, age=18}}`）与数组值（如 `tags=[a, b]`）。**已确认支持（Q3）。** |
| FR-C13 | **[X]** | P1 | **新增（G-3）**：在 `Map.toString()` 模式下，若**对象内**某条目在深度 1 处找不到任何 `=`，则系统应判定为「键值分隔符缺失」并进入报错定位（归入 FR-D8 已有分类）；**数组内**的条目无 `=` 属正常（数组元素本就无 `=`），不得报错。 |

### FR-D｜容错分层与报错定位（P1 核心）

> 上游文档的三层策略需要一个关键澄清：**「第 1 层标准解析」是相对于当前判定的来源格式而言的**。若来源判定为 Python 字面量，则单引号与 `True/False/None` 在第 1 层就是合法的——否则 Python 源在第 1 层必然失败，"分层"就失去意义。

| ID | 类型 | 需求描述 |
|---|---|---|
| FR-D1 | **[U]** | 系统应始终对**当前判定的来源格式**执行三层解析：第 1 层严格解析 → 第 2 层宽松修复 → 第 3 层报错定位。 |
| FR-D2 | **[U]** | 第 1 层应严格按该来源格式的规范解析，成功则直接输出，**不做任何修复、不显示修正提示**。 |
| FR-D3 | **[U]** | 第 2 层宽松修复应至少覆盖：键名补引号、单/双引号互转补齐、删除末尾多余逗号、剥离 Python `#` 行注释、补齐缺失的右括号/右方括号/右花括号、字符串内引号正确转义。 |
| FR-D4 | **[E]** | 当第 2 层修复成功时，系统应在输入区底部显示「已自动修正 N 处 ▾」提示条。 |
| FR-D5 | **[E]** | 当用户展开修正提示条时，系统应逐条列出每处修正：**行号 + 涉及片段 + 执行的修正动作**。 |
| FR-D6 | **[X]** | 若三层解析均失败，则系统应在输入区高亮出错行，并在提示区显示「第 N 行第 M 列：<原因>」。 |
| FR-D7 | **[S]** | 在解析失败状态下，系统应将输出区标记为「已过期」（置灰 + 角标），保留上一次成功结果供参考，但**禁用「复制」与「下载」按钮**。 |
| FR-D8 | **[U]** | 报错原因文案应至少区分以下类别：缺少右括号/右方括号/右花括号、引号未闭合、键值分隔符缺失、存在无法识别的字符、类型无法推断。 |
| FR-D9 | **[E]** | 当输入区为空时，系统不应显示任何报错，而应显示空状态占位文案。 |
| FR-D10 | **[X]** | 若解析失败且用户尚未手动锁定来源格式，则系统应在报错下方提示「可尝试手动切换来源格式」，并提供一键切换入口。 |
| FR-D11 | **[X]** | **新增（v1.3）**：若主干结构解析完成后仍存在未被消费的 token（尾部残留），系统应**报错**并给出残留首 token 的行列位置，**不得**静默忽略。错误文案应区分「尾部存在多余内容」与「检测到多个并列值（如 JSON Lines），本工具一次只处理一个值」。 |
| FR-D12 | **[U]** | **新增（v1.3）**：修正记录的类型应与实际修正动作一致。系统**不得**用「删除末尾多余逗号」标记「忽略残留内容」这类动作。 |
| FR-D13 | **[X]** | **新增（v1.3）**：若解析失败且检测到输入在主干结构之前存在疑似日志前缀（时间戳、日志级别、线程名等），系统应在报错信息中提供**一键入口**「剥离日志前缀后重试」；点击后截去前缀并重新解析。 |
| FR-D14 | **[E]** | **新增（v1.3）**：当用户点击「剥离日志前缀后重试」时，系统应在修正记录或提示条中**显式列出被剥离的前缀文本**，确保该操作可追溯。 |

> **FR-D11 与定位的一致性**（防止被误读为违背"容错优先"）：
> 「能救就救」针对的是**同一个值内部的语法残缺**（缺括号、多逗号、单引号）；
> 而**丢弃额外的值**不是修复，是**静默丢数据**。§10 R2 明确写着「静默错误比报错更危险」。

> **FR-D13 实现要点**：复用 lexer 的 Token 流定位第一个结构起始 token（`{` 或 `[`），
> 取其 `start` 偏移截取原文。**不要**用正则匹配时间戳 —— 实测会漏剥 `ERROR com.foo.Bar - {...}` 的 logger 名。
> 附属：BOM（`\uFEFF`）应在 lexer 层剥离，避免带 BOM 的 JSON 被误判为 Java 转义格式。

> **FR-D7 是一个有意的产品决策**：失败时保留旧输出（置灰）而不是清空，避免用户在排查时丢失参照物；但禁用复制/下载，杜绝"复制了过期结果而不自知"这类静默错误。

| ID | 类型 | 需求描述 |
|---|---|---|
| FR-I1 | **[E]** | 在转义 tab 中，系统应对整段文本执行转义或反转义，**不得**尝试解析其结构。 |
| FR-I2 | **[U]** | 转义风格应至少支持：JSON 字符串转义、Java 字符串转义、URL 百分号编码、Base64。每种均支持**双向**。 |

| FR-I4 | **[U]** | Base64 编解码应**始终按 UTF-8 字节序列**处理。 |
| FR-I5 | **[U]** | **新增（v1.4）**：转义 tab 应始终提供**显式的方向二选一**：「去除转义」与「增加转义」，常驻可见并标明当前选中项。方向**不得**藏进按钮的隐式翻转。默认方向为「增加转义」，且该选择应持久化（历史偏好覆盖默认值）。 |
| FR-I6 | **[E]** | **新增（v1.4）**：当用户执行「去除转义」时，若整段文本被一对**配对的外层引号**包裹，系统应先剥离该对引号再反转义，并在状态条**显式提示**「已自动去除外层引号」。**不得**剥离中间存在未转义同种引号的文本。 |
| FR-I7 | **[U]** | **新增（v1.4）**：任一风格下，「增加转义」的结果再执行「去除转义」应还原为原文（往返一致）。 |

> **FR-I5 的理由（实测缺陷）**：v1.1.0 把方向做成了底部按钮的隐式翻转 ——
> 按钮只显示当前方向（「编码」/「解码」），用户点一下才知道它其实是切换器。
> 结果测试时用户反馈**「没有去除转义的选项」**。这不是功能缺失，是**可见性缺失**，
> 但用户体验上等价。故改为常驻二选一 + 底部按钮明确写出「反向会变成什么」。

> **FR-I6 的理由（真实复制场景）**：从 Java / JSON 代码里复制出来的字符串常量
> **自带外层引号**，如 `"{\"a\":1}"`。不剥壳会得到 `"{"a":1}"` —— 外层引号残留，
> 用户还得手删。剥壳**不是**解析结构（FR-I1 禁止的），只是脱掉「常量外壳」。
>
> **安全判据**：不能只比较首尾字符，要扫描确认中间的同种引号**都被反斜杠转义**，
> 否则 `a" + "b` 会被误判。四种风格都安全：url 编码后 `"` → `%22`，base64 字母表不含 `"`。

> **FR-I4 实测硬约束**：原生 `btoa('中文')` 抛 `InvalidCharacterError`（只接受 Latin-1）。
> 必须走 `TextEncoder → btoa` 与 `atob → TextDecoder`。

> **架构注记**：转义 tab 是**纯字符串**通道（文本 → 文本），**不经过 IR**，
> 与转换/格式化 tab（IR → 文本）本质不同。**不得**硬塞进 `convert()`。

## 七、关键算法与交互逻辑细则

### 7.1 来源格式打分算法（对应 FR-B3）

对 **lexer 产出的 Token 流**扫描（仅统计字符串字面量**外部**的信号），各信号计分，总分最高者胜出：

| 信号 | 指向来源 | 分值 | 次数上限 |
|---|---|---|---|
| 裸字面量 `True` / `False` / `None` | Python 字面量 | +3 | 计满 2 次封顶（+6） |
| 单引号包裹的键或值 | Python 字面量 | +2 | 计满 2 次封顶（+4） |
| 行内 `#` 注释 | Python 字面量 | +2 | 计满 2 次封顶（+4） |
| `(` 作为容器起始 | Python 字面量 | +2 | 计满 2 次封顶（+4） |
| 深度 1 处出现 `=` 作为键值分隔 | Map.toString() | +3 | 计满 2 次封顶（+6） |
| 裸字面量 `true` / `false` / `null` | 标准 JSON | +3 | 计满 2 次封顶（+6） |
| 双引号包裹的键 | 标准 JSON | +2 | 计满 2 次封顶（+4） |
| **整段被双引号包裹**且内部存在 `\"` | Java 转义字符串 | **+4（存在即计一次，不累加）** | — |

**修订要点（C-2，技术评审硬冲突）**：

1. **Java 转义信号必须加结构前提** —— 只有「去空白后首字符为 `"` 且末字符为 `"`（整段被包裹）」且内部存在 `\"` 时才计分，且**不按次数累加**。
   > **原规则的缺陷**：`{"msg": "he said \"hi\""}` 是**合法标准 JSON**，但按原规则 `\"` × 2 = +8 会压过 JSON 的 +5，被误判为 Java 转义字符串并反转义成非法文本。加结构前提后该例不命中 Java 信号，正确判定为 JSON。
2. **所有信号设置次数上限（每类最多计 2 次）** —— 避免长文本中 200 个单引号（+400）压倒一切其他信号，让打分退化为"谁文本长谁赢"。
3. **打分器复用 lexer 的 Token 流**（FR-B3）—— 不得另写一套引号状态机。否则打分器与解析器对"什么是字符串边界"的理解会漂移，这是此类工具最经典的 bug 源。

**裁决规则**：
1. 取总分最高的候选；
2. **平局 → 判定为「标准 JSON」**（FR-B4）；
3. `Map.toString()` 信号单独达到 +3 且 JSON 信号为 0 时，直接判定为 Map.toString()（避免混合信号下的模糊）；
4. 无任何信号（如纯数组 `[1,2,3]`）→ 判定为「标准 JSON」；
5. 判定后若第 1 层解析失败，按 **FR-B11** 依次回退尝试其余三种格式。

**字符串外部判定**：由 lexer 保证——Token 流中字符串字面量已是独立 token，其内部的 `True`、`null`、`=`、`#` 天然不会被计入。

**示例推演**：

| 输入 | 命中信号 | 判定 |
|---|---|---|
| `{'name': '张三', 'vip': True}` | Python: 单引号(+4 封顶) + True(+3) = 7 | Python 字面量 |
| `{"name": "张三", "vip": true}` | JSON: 双引号键(+4 封顶) + true(+3) = 7 | 标准 JSON |
| `{name=张三, age=18}` | Map: `=`(+6 封顶)；JSON: 0 | Map.toString() |
| `{\"name\": \"x\"}` | Java 转义: 整段包裹 + `\"`(+4)；JSON: 双引号键(+2) | Java 转义字符串 |
| `[1, 2, 3]` | 无信号 | 标准 JSON（默认） |
| **C-2 反例** `{"msg": "he said \"hi\""}` | Java 转义: 不满足整段包裹 → **0**；JSON: 双引号键(+4) = 4 | 标准 JSON ✅ |

### 7.2 Python 侧引号选择算法（对应 FR-A9）

> 这是上游文档遗留问题 Q1 的**推荐解法**。目标：输出必须能被 `ast.literal_eval` 正确求值（FR-A10），同时避免无谓的转义噪音。

对每个待输出的字符串值，按序判定：

| 条件 | 采用形式 | 示例 |
|---|---|---|
| 不含 `'` 且不含 `"` | 单引号（Pythonic 默认） | `abc` → `'abc'` |
| 含 `'` 且不含 `"` | **双引号**（无需转义） | `it's` → `"it's"` |
| 含 `"` 且不含 `'` | 单引号 | `say "hi"` → `'say "hi"'` |
| 同时含 `'` 与 `"` | 单引号，内部 `'` 转义为 `\'` | `it's "x"` → `'it\'s "x"'` |
| 含换行/制表等控制字符 | 双引号 + 标准转义 | 含 `\n` → `"a\nb"` |
| 含反斜杠 `\` | 按上述规则选引号后，将 `\` 转义为 `\\` | `a\b` → `'a\\b'` |

**键名与字符串值适用同一算法。**

**为什么推荐「含单引号时用双引号」而不是 `'it\'s'`**：Python 中 `"it's"` 与 `'it\'s'` 完全等价，但前者零转义、可读性更好，也降低了转义逻辑出错的概率。代价是输出风格不"纯单引号"——对自用工具而言，可读性优先于风格统一。

### 7.3 `Map.toString()` 解析与类型推断（对应 FR-C4/C5/C12）

**解析流程**：

1. 检测最外层是否由 `{` `}` 包裹；若是则按对象解析，否则尝试按数组解析（`[a, b]`）。
2. 在**括号深度 1** 上按 `,` 切分条目（字符串内的 `,` 不切分）。
3. 每个条目在**深度 1** 处找**第一个** `=`，左侧去空白为键，右侧去空白为值。
4. 值递归处理：
   - 以 `{` 开头 → 递归解析为嵌套对象（FR-C12）
   - 以 `[` 开头 → 递归解析为数组（FR-C12）
   - 否则 → 按 FR-C5 做类型推断

**类型推断表**：

| 原始值 | 推断类型 | 输出（Python 侧） |
|---|---|---|
| `18` | 数字 | `18` |
| `3.14` / `-2` / `1e5` | 数字 | 原样透传（FR-A11） |
| `true` / `TRUE` / `True` | 布尔 | `True` |
| `false` / `FALSE` / `False` | 布尔 | `False` |
| `null` / `NULL` / `None` | null | `None` |
| `张三` | 字符串 | `'张三'` |
| `0012` | **数字** → 用户可手动改为字符串 | `12` ⚠️ 这是推断的固有风险，靠 FR-C6 下拉兜底 |
| `` （空值） | 字符串 | `''` |

> **`0012` 这类前导零数字是类型推断的固有盲区**，无法从文本判断意图。这正是 FR-C6 类型下拉框存在的意义——不追求推断 100% 正确，而是提供低成本的人工纠正通道。

### 7.4 三层解析流程（对应 FR-D1）

```
输入文本
   ↓
来源判定（§7.1）── 手动锁定？── 是 → 跳过判定，直接用锁定格式
   ↓
第 1 层：严格解析（按该来源格式的规范）
   ↓ 成功 → 直接输出，无修正提示
   ↓ 失败
第 2 层：宽松修复（FR-D3 六类修复，逐条应用并记录）
   ↓ 成功 → 输出 + 显示「已自动修正 N 处」（FR-D4）
   ↓ 失败
第 3 层：报错定位 → 高亮行 + 「第 N 行第 M 列：原因」+ 输出区标记过期（FR-D6/D7）
```

**第 2 层修复的记录格式**（供 FR-D5 展开显示）：

```
第 3 行：键名 name 补充引号        {name: 1}      → {"name": 1}
第 7 行：删除末尾多余逗号          [1, 2, ]       → [1, 2]
第 12 行：剥离行注释               'a': 1,  # 备注 → 'a': 1,
第 15 行：补齐缺失的右花括号        （行尾）        → }
```

### 7.5 界面状态机

| 状态 | 进入条件 | 输出区 | 可用按钮 | 提示区 |
|---|---|---|---|---|
| **空** | 输入为空 | 空状态占位 | 全部禁用 | 引导文案：「粘贴内容即可自动转换」 |
| **已解析** | 第 1 层解析成功 | 正常高亮结果 | 全部可用 | 判定条显示来源（自动/手动标记） |
| **已修复** | 第 2 层修复成功 | 正常高亮结果 | 全部可用 | 「已自动修正 N 处 ▾」可展开 |
| **回退成功**<br>**（v1.2 新增）** | 首选格式三层均失败，按 FR-B11 尝试其他格式成功 | 正常高亮结果 | 全部可用 | 「已按 X 格式解析」+ 该格式下的修正提示（若有） |
| **解析失败** | 三层均失败 | 上一结果**置灰**+「已过期」角标 | 仅「转换」可用；复制/下载/格式化/压缩禁用 | 「第 N 行第 M 列：原因」+ FR-D10 切换建议 |
| **大文本降级** | 字符数 > 100,000 | 高亮关闭或实时关闭（按档） | 全部可用 | 「已关闭高亮（文本较大）」/「已关闭实时转换」 |
| **转换超时** | 单次 > 3 秒 | 保持上一结果 | 全部可用 | 「转换超时，建议用放大页面或拆分文本」 |

**状态迁移要点**：
- 任一状态 → **空**：清空输入（同时清除手动锁定与类型覆盖，FR-B7/FR-C8）
- **解析失败** → **已解析/已修复**：用户编辑输入后重新解析成功，输出区角标移除，按钮解禁
- **已修复** → **已解析**：输入变化后重新解析且无需修复，修正提示条消失

### 7.6 手动类型覆盖的生命周期（对应 FR-C8）

这是 `Map.toString()` 模式下最容易做错的一环：**用户改了类型后，输入文本再变，覆盖该怎么办？**

**规则**：覆盖记录绑定在「值在结果结构中的路径」上（如 `/user/age`），而非行号或索引。

| 事件 | 覆盖的处理 |
|---|---|
| 用户修改类型下拉 | 记录 `路径 → 指定类型`，标记该值为人工指定（FR-C9） |
| 输入文本变化并重新解析 | 按路径重建覆盖：路径仍存在 → 保留；路径已消失 → 丢弃该项 |
| 用户切换来源格式 | **保留**覆盖（值集合通常不变，保留对用户更有利） |
| 用户点击「清除覆盖」 | 清空全部，恢复自动推断 |
| 输入区清空 | 清空全部 |
| 弹窗关闭 | 清空全部（不持久化，与 NG1 一致） |

> **按路径而非按行号记录**的原因：行号会随格式化和文本微调整体漂移，而结构路径是稳定的。这避免了"用户改了 3 个类型，加一行注释后全错位"这种最让人恼火的情况。

### 7.7 转义对照表（对应 FR-A12，新增 D-8）

字符串值中的特殊字符按目标语言转义。** FR-A7（中文不转义）不受影响** —— 中文属可打印字符，两个方向均原样输出。

| 字符 | 标准 JSON 输出 | Python 字面量输出 | 说明 |
|---|---|---|---|
| `"` U+0022 | `\"` | `"` 或 `\"`（取决于 §7.2 选中的引号） | 仅当与包裹引号相同时转义 |
| `\` U+005C | `\\` | `\\` | 双向均必须转义 |
| 换行 U+000A | `\n` | `\n` | |
| 回车 U+000D | `\r` | `\r` | |
| 制表 U+0009 | `\t` | `\t` | |
| 退格 U+0008 | `\b` | `\b` | |
| 换页 U+000C | `\f` | `\f` | |
| 其余 U+0000–U+001F | `\u00XX`（小写 4 位十六进制） | `\xXX` | JSON 无 `\x` 语法，必须用 `\u` |
| U+2028 行分隔符 | `\u2028` | `\u2028` | 建议转义：避免贴进 JS 源码时被当作换行 |
| U+2029 段分隔符 | `\u2029` | `\u2029` | 同上 |
| 中文等 CJK | **原样** | **原样** | FR-A7 |

> **为什么显式列出 U+2028/2029**：这两字符在 JSON 中合法、在 Python 中也合法，但在 JavaScript 源码中会被当作行终止符。用户转换结果常要贴进 JS 代码，转义掉的代价极小，收益是避免一类难以排查的问题。

## 九、成功指标

> **重要说明**：本产品为个人自用工具，且 FR-H3 明确禁止任何埋点。**因此不存在 DAU / 留存 / 转化率这类指标**——即便想统计，也因禁用上报而无法获取。以下指标全部通过**本地样本集回归 + 人工记录**获得，这是与产品定位一致的、诚实可行的度量方式。

### 9.1 北极星指标

> **一次搞定率**：粘贴后无需任何手动干预（切换来源、改类型、手工改文本）即得到可直接使用的输出的比例。

**目标**：30 条真实样本集 ≥ 90%；** stretch 目标**：100%。

**测量方式**：建立 `samples/` 目录，收集 30 条本人真实使用场景的输入文本及其期望输出，作为回归测试集。每次改动解析器后运行全量回归，统计通过率。

### 9.2 支撑指标

| 层 | 指标 | 目标 | 测量方式 |

### ✅ 已确认（2026-09-20，采纳推荐值）

| # | 问题 | 确认结论 | 已固化到 |
|---|---|---|---|
| **Q1** | `"it's"` 转 Python 时输出哪种引号形式？ | **含单引号且不含双引号 → 使用双引号**（`"it's"`）；同时含两种引号时才转义为 `\'`。完整算法见 §7.2 | FR-A9、AC-13/14/15 |

>
> Q3 由 P2 升为 **P1**，将随 M2（容错与报错）一并实现，理由见 §7.3：递归下降解析器的增量成本很小，而嵌套 Map 在真实日志中相当常见。
